# Исправленные ошибки

## Telegram polling мог оставаться на зависшем соединении

При диагностике 2026-11-16 production использовал старый HTTP-прокси
`94.158.57.216:3128`. Последние ошибки подключения датированы 2026-11-14;
после них журнал polling молчал, Telegram сохранял 7 необработанных обновлений,
а процесс держал соединение с прокси. Это признаки зависания запроса; точное
внутреннее место остановки не установлено. SOCKS5 на VPN-сервере
`13.143.194.252:14837` проверен отдельно через Telegram `getMe`.

В `src/telegram.ts` добавлены абсолютная отмена запроса через 40 секунд и
повтор через 5 секунд; одного axios timeout недостаточно для такой гарантии.
Остановка отменяет запрос, проверки поколения после await и внутри пачки
не допускают старые callbacks и изменение offset после stop/start.

Регрессия `src/telegram.spec.ts`: окончательные тесты на исходной реализации —
5 failed / 4 passed; после исправления и добавления двух тестов гонки —
11 passed. Новые тесты гонки отдельно дали RED 2 failed / 9 passed до проверок
поколения. Полный набор — 157 passed, сборка и независимое ревью успешны.
Поставка 2026-11-17: исправление установлено на ПК вместе с SOCKS5.
Очередь Telegram уменьшилась до 0, новый секретный тестовый ответ получен
через MCP и одноразовую ссылку. Подробности: `ai/FEATURES.md`.

## Ответ на заголовок Telegram-вопроса не принимался

Симптом: ответ реплаем на сообщение с текстом вопроса оставлял вопрос в
`pending`. Причина: вопрос отправляется заголовком и отдельным приглашением
ForceReply, но поиск учитывал только ID приглашения, хотя заголовок тоже
предлагает ответить на него.

Решение: `AskStore.byTelegramMessage()` ищет по текущим
`telegram_message_id` и `telegram_anchor_message_id`. Ответ на приглашение
сохранён; после отправки новой попытки старые ID не принимаются.

Проверка 2026-11-16: `npm test -- --runInBand src/asks.spec.ts` — до исправления
4 failed / 27 passed, после 31 passed. Полный `npm test -- --runInBand` —
146 passed; `npm run build` успешен; независимое ревью без замечаний.
Файлы: `src/asks.ts`, `src/asks.spec.ts`.
Поставка 2026-11-17: исправление установлено на ПК. Новый тестовый ответ
получен через Telegram; выбор цели реплая отдельно не протоколировался.
Контракт ответа на заголовок подтверждён автоматическими тестами. Связь с
конкретным первоначальным неполученным ответом не доказана.

## Ответ Telegram-опроса оставался pending

Симптом: вариант в опросе выбран, но `wait_answer` продолжает возвращать
`pending`. Причина: `poll_answer` мог прийти до регистрации promise в
`waiting` и отбрасывался. Решение: выбор сразу сохраняется общим путём
`deliver()`, который также будит waiter, если он уже существует. Покрыто
регрессионным тестом быстрого ответа.

## Ошибка Telegram оставляла вечный pending

Симптом: при сетевой ошибке Bot API вопрос не приходил, а клиент продолжал ждать.
Решение: ошибка отправки переводит ask в `failed`; MCP возвращает явный статус и
предлагает оставить видимый текстовый вопрос.

## Windows-установщик не видел станции и ломал алиасы

PowerShell 5 требовал UTF-8 BOM, а `Get-Content` без `-Encoding UTF8` портил
русские имена. Node mDNS также не всегда получает multicast при занятом Bonjour
порту 5353. Установщик теперь сохраняет UTF-8 и при необходимости использует
zeroconf из уже настроенного assistant.

## Bridge игнорировал колонку по умолчанию

Симптом: вызов `alice_say` без `station` озвучивался на первой колонке клиента,
а не на настроенном `VOICE_STATION=кабинет`. Причина: `VoiceService` отправлял в bridge
`station: null`, и выбор дефолта неожиданно переходил к LAN-клиенту.

Решение: сервер передаёт в bridge явную цель или настроенный `config.voice.station`.
Добавлен регрессионный тест в `src/voice/bridge.transport.spec.ts`; живая проверка вернула
`кабинет via pi`.

## Ошибка соседней job скрывала результат выбранной job

Симптом: tracker сообщал `failed` для успешной либо выполняющейся выбранной
GitLab job, если соседняя проверка уже упала в родительском pipeline.
Причина: общий статус pipeline проверялся раньше статуса выбранной job.

Решение: `plugins/human4ai-control/scripts/lib/ci-worker.cjs` сначала находит
и классифицирует выбранную job. Ошибка соседней job не отменяет её успех и
не прерывает выполняющуюся либо доступную к запуску job. Отмена, блокировка
или обязательное ручное действие собственного pipeline прекращают ожидание.
Ожидание всего pipeline сохраняет прежний контракт.

Проверка: RED → GREEN в
`plugins/human4ai-control/scripts/test/ci-worker-gitlab-target.test.cjs`,
26 тестов CLI и независимое ревью. После локальной установки реальная
успешная job `29831564` в failed pipeline `5115449` распознана как `success`.


## Docker CMS блокировал исходящие соединения Human4AI

2026-11-17 вопрос `ask_d9c7023bc59349d0a699` завершился `failed` с
`Proxy connection timed out`. Подключение к SOCKS5 работало с Windows и WSL,
но из контейнера истекало по таймауту. В filter отсутствовали правила моста
`br-40eddf6c6cc4`, а политика FORWARD оставалась DROP. MASQUERADE сохранился.
Временные разрешения только app-контейнер → SOCKS5 и установленного обратного
трафика восстановили `getMe` за 444 мс, подтвердив место блокировки.

Human4AI и CMS имели одинаковые netns и boot ID. Docker CMS стартовал в 01:22
после Docker Human4AI в 00:01, управлял iptables по умолчанию и оставил цепочки
только для docker0, хотя его контейнер использовал host network. Это соответствует
[конфликту нескольких Docker daemon](https://docs.docker.com/reference/cli/dockerd/#run-multiple-daemons).

Решение: Docker CMS переведён в host-only режим без управления bridge, iptables,
ip6tables и ip-forward; остальные поля конфигурации сохранены. Старый CMS Docker
остановлен, штатные правила восстановлены перезапуском Docker Human4AI через
его SCM lifecycle. Временные правила удалены, FORWARD DROP сохранён. После нового
запуска CMS и сайта все IPv4 filter/NAT правила Human4AI совпали с baseline.
Telegram `getWebhookInfo` успешен, backlog 0; контрольный вопрос через MCP получил
ответ, подтверждение REST вернуло 200. Значение ответа в журнал не внесено.

Проверки: `dockerd --validate`, `bash -n`, объединение JSON с сохранением data-root,
отказ валидации без замены файла; независимое ревью. Новые автоматические тесты
не добавлялись по исключению для операционных настроек. Human4AI health 200,
CMS health 204, сайт 200, S3 LAN health 200. Службы восстановлены через SCM;
проверенные копии SQLite и PostgreSQL сохранены на ПК и Mac; исходные правила — на ПК.
